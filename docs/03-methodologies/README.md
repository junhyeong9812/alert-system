# 방법론 지도

> 실패를 알림까지 안정적으로 전달하는 방법론을 **단일 / 흐름 / 시스템** 범주로 나누고,
> 마지막으로 세 범주를 묶은 **통합** 구조를 둔다. 최초 설계(id 왕복 핸드셰이크)도 방법론 중 하나인 **기준선**으로 취급한다.

관련: [실패 유형 분류](../01-problem/02-failure-taxonomy.md) · [실험 계획](../04-experiments/experiment-plan.md)

---

## 1. 범주

| 범주 | 해결하는 질문 | 대상 실패 | 신호 형태 |
|------|-------------|----------|----------|
| **단일** (`SG`) | 한 서비스에서 생긴 실패 사실을 어떻게 유실 없이·소음 없이 알림까지 보내나 | F1, F2 | 존재 |
| **흐름** (`FL`) | 서비스를 가로지르는 실패를 어떻게 감지·진단하나 — 동기 오케스트레이션과 이벤트 코레오그래피를 구분 | F3, F4, F5 | 존재 + 부재 |
| **시스템** (`SY`) | 스스로 보고할 수 없는 서버·인프라·알림 경로의 실패를 어떻게 잡나 | F6, F7 (+ F1·F2 비율 이상) | 상태 |
| **통합** (`IN`) | 세 범주를 어떻게 하나의 구조로 조합하나 | F1 ~ F7 | 전부 |

**하나의 방법론으로 전체를 덮을 수 없다.** 전체 구조는 범주별로 하나 이상을 골라 조합한다.
그래서 각 방법론 문서의 "전체 구조"에는 그 방법론이 직접 담당하지 않는 범주를 무엇으로 채우는지(특히 **운영 경로**)를 함께 그린다.

### 우선순위 표기 규칙
- **기준선**: 비교 기준. 실험하되 채택 후보는 아니다.
- **P1**: 반드시 실험한다. 최종 구조 후보.
- **P2**: 여력이 있으면 실험한다. 특정 조건(인프라 제약, 결합 최소화 요구)에서의 대안.
- **가설**: 실험 전 제안이다. 실험 결과로 확정하거나 수정한다.
- 모든 우선순위는 실험 전 판단이다. 바뀌면 근거를 실험 결과 문서에 남긴다.

## 4. 방법론 조합 규칙

```
 전체 구조 = 단일 슬롯 (SG-02 | SG-03 | SG-05 | SG-06 | SG-07) [+ SG-04 계층]
           + 흐름 슬롯 (FL-01 | FL-02 | FL-03) + FL-04 [+ FL-05]
           + 시스템 슬롯 SY-01 + SY-02 + SY-03
```

- **SG-04, FL-04, FL-05는 다른 방법론 위에 얹는 계층**이다. 단독으로는 구조가 되지 않는다.
- **흐름 슬롯은 통신 모드에 종속된다.** FL-01은 동기 REST, FL-02는 이벤트 코레오그래피, FL-03은 이벤트 + 중앙 상태다.
- **시스템 슬롯은 거의 고정**이다. 서로 다른 신호(내부 메트릭 / 외부 프로빙 / 메타 heartbeat)를 맡으므로 대체 관계가 아니라 보완 관계다.

## 5. 방법론 문서 템플릿

각 방법론 문서는 같은 구성을 따른다.

```
# <ID>. <이름>
> 상태 · 범주 · 대상 실패 · id 의존도

## 한 줄 요약
## 핵심 아이디어
## 전체 구조                ← 도메인 경로 + 흐름 경로 + 운영 경로 + 메타 경로
## 동작 흐름                ← 정상 / 실패 시나리오
## 보장 속성                ← 유실 · 중복 · 순서 · 지연
## 알림 실패 처리
## 책임 경계 (DDD)
## 트레이드오프             ← 장점 / 비용
## 못 잡는 것 → 보완
## 실험 가설                ← 실험 계획 문서의 해당 절로 링크
```
