# SG-06. Pull 폴링 (커서)

> **상태**: P2 · **범주**: 단일 · **대상 실패**: F1, F2 (+ F6 부분) · **id 의존도**: 낮음 — 진행 상태는 **커서(마지막으로 읽은 위치)**

## 한 줄 요약
생산자는 실패를 자기 DB의 `failure_log`에 기록만 하고, **알림 서비스가 주기적으로 가져간다**(`GET /failures?after=<cursor>`). 생산자는 알림 서비스의 존재를 모른다.

## 핵심 아이디어
- push의 반대. 전달 책임이 처음부터 끝까지 **소비자(알림 서비스)**에 있다.
- 진행 상태는 알림 서비스가 서비스별로 저장하는 **커서**(단조 증가 시퀀스) 하나다.
- 알림 서비스가 죽어도 생산자의 `failure_log`에 남아 있으므로, 복구 후 커서부터 이어서 가져온다.
- **폴링 실패 자체가 신호다**: 서비스가 응답하지 않으면 그 서비스가 아프다는 뜻 → F6 일부를 부수적으로 감지한다.

## 전체 구조

```
 [도메인 경로]
 ┌─────────────────────────────┐          ┌──────────────────────────────────────────┐
 │ order-service                │          │ notification-service                      │
 │  tx: biz + INSERT failure_log│          │  poller (서비스별, 주기 N초)                │
 │       (seq BIGSERIAL, …)     │◀─────────│   GET /failures?after=cursor&limit=500    │
 │  GET /failures?after=&limit= │─────────▶│   → 처리(SG-04 집계) → cursor 저장(같은 tx)│
 └─────────────────────────────┘  응답     │   실패/타임아웃 → poll_fail_total++         │
 ┌─────────────────────────────┐          │                                          │
 │ product-service  (동일)      │◀─────────│  cursors: {order: 18231, product: 9921, …}│
 └─────────────────────────────┘          │  Notifier ─┬─ Slack  └─ Email             │
 ┌─────────────────────────────┐          │                                          │
 │ shipping-service (동일)      │◀─────────│                                          │
 └─────────────────────────────┘          └──────────────────────────────────────────┘

 [흐름 경로]   FL-05(Reconciliation)와 궁합이 좋음 — 같은 폴링 구조로 흐름 상태도 조회
 [운영 경로]   SY-01: poll_fail_total, poll_lag(서비스 최신 seq − 커서) 수집
               연속 폴링 실패 → "서비스 응답 없음"(SY-02와 신호 중복 → 억제 규칙 필요)
 [메타 경로]   SY-03
```

## 동작 흐름

| 상황 | 결과 |
|------|------|
| 알림 서비스 다운 | failure_log에 누적 → 복구 후 커서부터 일괄 수집 → 유실 없음 |
| 처리 후 커서 저장 전 크래시 | 같은 구간 재수집 → 중복 처리 (SG-04 집계면 count 이중 가산 주의 → 커서와 집계를 같은 tx로) |
| 생산자 서비스 다운 | 폴링 실패 → 그 자체가 신호. 실패 기록은 서비스 DB에 남아 있음 |
| 시퀀스 공백 (롤백된 tx) | BIGSERIAL 공백은 정상 — 커서는 `>`로 비교하므로 무해. 단 **늦게 커밋된 낮은 seq**는 건너뛸 수 있음 → 커밋 시점 기준 정렬 또는 안전 지연(N초 이전 것만 수집) 필요 |

### 시퀀스 가시성 문제 (중요)
```
 tx A: seq=101 할당 ── (느림) ──────────────── COMMIT
 tx B: seq=102 할당 ── COMMIT
 poller: after=100 → [102] 가져감 → cursor=102 → seq 101은 영원히 건너뜀
```
→ 대응: `created_at < now() - safety_lag` 조건으로 아직 진행 중일 수 있는 tx 구간을 제외한다. 알림 지연이 safety_lag만큼 늘어난다.

## 보장 속성

| 속성 | 수준 | 비고 |
|------|------|------|
| 유실 | 없음 (가시성 문제 대응 시) | |
| 중복 | 커서-처리 원자성에 의존 | |
| 순서 | 서비스 단위 seq 순서 | |
| 지연 | 폴링 주기 + safety_lag (수 초) | push 계열보다 김 |

## 알림 실패 처리
발송 실패는 알림 서비스 내부 사다리(재시도 → fallback → DLQ). 커서는 **수집**의 진행이고 **발송**의 진행이 아니다. 수집한 것은 알림 서비스 DB에 먼저 저장해야 한다.

## 책임 경계 (DDD)
- 생산자는 "실패 기록 + 조회 API"만 제공. 알림 서비스에 대한 의존 0.
- 대신 조회 API가 **공개 계약**이 된다(Open Host Service).
- 알림 서비스가 모든 생산자의 주소를 알아야 한다 — 의존 방향이 역전됨(알림 → 서비스).

## 트레이드오프

| 장점 | 비용 |
|------|------|
| 브로커·relay 없음, 생산자 코드 최소 | 지연이 큼 (주기 + safety_lag) |
| 알림 서비스가 페이스 조절 (backpressure 자연 해결) | 서비스 수 × 주기만큼 폴링 부하 (실패가 없어도) |
| 폴링 실패 = 서비스 상태 신호 | 시퀀스 가시성 문제 |
| 구조가 매우 단순 | 알림 서비스가 서비스 목록을 관리 |
