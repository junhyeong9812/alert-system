# SG-03. 브로커 at-least-once + 오프셋

> **상태**: P1 · **범주**: 단일 · **대상 실패**: F1, F2 · **id 의존도**: 낮음 — 진행 상태는 **로그 위치(오프셋)**

## 한 줄 요약
메시지별 ack 대신 **내구성 있는 로그(Kafka)의 소비 위치**로 진행을 관리한다. 소비자는 발송에 성공한 뒤에 오프셋을 커밋하고, 실패하면 재시도 토픽과 DLQ 토픽으로 넘긴다.

## 핵심 아이디어
- 브로커가 "받았다"를 보장한다(`acks=all`). 생산자 책임은 브로커 수락에서 끝난다.
- 소비자의 진행 상태는 메시지 id 목록이 아니라 **오프셋 하나**다. 크래시하면 마지막 커밋 위치부터 다시 읽는다 → 유실 없음, 중복 가능.
- 로그는 남아 있으므로 **재생(replay)**이 가능하다. 알림 로직을 고친 뒤 과거 이벤트를 다시 흘려볼 수 있다.
- 생산자 쪽 dual write는 outbox로 막는다(relay가 HTTP 대신 Kafka로 발행).

## 전체 구조

```
 [도메인 경로]

                                                   ▼                   │
```

## 동작 흐름

| 상황 | 결과 |
|------|------|
| 알림 서비스 다운 | 메시지는 Kafka에 쌓임(lag 증가) → 복구 후 오프셋부터 소비 → **유실 없음** |
| 발송 성공 후 커밋 전 크래시 | 재시작 후 같은 메시지 재소비 → Slack 중복 1건 |
| Slack 장애 | 메인 토픽을 막지 않고 재시도 토픽으로 우회 → 다른 메시지는 계속 처리 |
| 브로커 다운 | relay가 발행 실패 → outbox에 누적 → 브로커 복구 후 발행 |
| 특정 메시지 반복 실패 (poison) | 재시도 소진 → DLQ, 메인 흐름 영향 없음 |

### head-of-line blocking 주의
재시도를 메인 토픽에서 하면(같은 메시지를 계속 재시도) 같은 파티션의 뒤 메시지가 모두 멈춘다. 그래서 **재시도 토픽을 분리**한다. 대신 재시도 메시지는 순서가 뒤로 밀린다.

## 보장 속성

| 속성 | 수준 | 근거 |
|------|------|------|
| 유실 | **없음** | outbox + `acks=all` + 처리 후 커밋 |
| 중복 | 있음 (드물게) | 커밋 전 크래시, relay 재발행 — 필요하면 소비자 멱등 체크(SG-02의 inbox)를 결합 |
| 순서 | 파티션 키 단위 보장 (재시도 메시지 제외) | |
| 지연 | relay 주기 + 소비 지연 (~수백 ms) | |

## 알림 실패 처리
재시도 토픽(지연 계층) → fallback → DLQ 토픽 → DLQ 적재량 메트릭 → 운영 경로. DLQ 재처리 = DLQ 토픽을 메인 토픽으로 재발행.

## 책임 경계 (DDD)
- 생산자: outbox → 브로커 수락까지. 알림 서비스의 존재조차 모름(토픽만 앎).
- 알림: 소비 · 발송 · 재시도 · DLQ.
- 브로커: 내구성과 재생 — **"받았다"의 책임을 인프라가 가져간다.**

## 트레이드오프

| 장점 | 비용 |
|------|------|
| 생산자-알림 완전 분리 (토픽이 계약) | Kafka 운영·리소스 (로컬에서도 메모리 큼) |
| 재생 가능 → 알림 정책 변경 후 재검증 | 메시지별 재시도/DLQ를 직접 구현 |
| 알림 서비스 장기 다운에도 버퍼 | 중복을 원천 차단하지 않음 |
| 소비자 수평 확장 (파티션 수까지) | 재시도 시 순서 깨짐, 파티션 수가 확장 상한 |
