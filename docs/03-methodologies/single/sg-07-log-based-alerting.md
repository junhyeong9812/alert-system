# SG-07. 로그 기반 알림

> **상태**: P2 · **범주**: 단일 · **대상 실패**: F2 (주력), F1 (부분), F6 (부분) · **id 의존도**: 없음

## 한 줄 요약
서비스는 구조화 로그(JSON)를 stdout으로 남기기만 한다. 로그 수집기(Alloy)가 Loki로 보내고, **Loki 규칙(LogQL)**이 패턴·빈도를 평가해 Alertmanager로 알림을 보낸다. 서비스 코드에 알림 로직이 0줄이다.

## 핵심 아이디어
- 이미 모든 서비스가 남기는 로그를 알림 입력으로 재사용한다.
- 알림은 **로그 스트림에 대한 쿼리 결과**다: `sum by (service, error_code)(count_over_time({level="error"}[1m])) > 10`
- 로그에 traceId·orderId 같은 맥락이 남아 있으므로, 알림에서 로그 조회 링크로 바로 넘어갈 수 있다.
- 메트릭(SY-01)과 달리 카디널리티 제약이 약하다(로그 본문에 orderId를 담아도 됨).

## 전체 구조

```
 [도메인 경로]
 ┌────────────────────────┐ stdout JSON
 │ order/product/shipping │ {"ts":…,"level":"error","service":"shipping",
 │  (알림 코드 없음)        │  "error_code":"ADDRESS_INVALID","category":"F1",
 └──────────┬─────────────┘  "trace_id":"4bf9…","order_id":1832, "msg":"…"}
            ▼ docker log driver / 파일
 ┌────────────────────────┐
 │ Grafana Alloy          │  라벨 추출: service, level, category (저카디널리티만)
 └──────────┬─────────────┘
            ▼
 ┌────────────────────────┐   ruler (평가 주기 15s)
 │ Loki                   │── LogQL 규칙 ──▶ ┌──────────────┐  webhook
 └────────────────────────┘                  │ Alertmanager │────────────▶ notification-service
                                             └──────────────┘                (라우팅·Notifier)
                                                     └── 또는 채널 직접 (Slack/Email)

 [흐름 경로]   trace_id로 서비스 간 로그를 묶어 조회 (FL-04와 결합) — 부재 감지는 로그로 어렵다
 [운영 경로]   이 방법론 자체가 운영 경로와 같은 스택(Alertmanager)을 공유
               SY-01: Alloy 전송 실패·지연, Loki ingestion rate, ruler 평가 실패 수집
 [메타 경로]   SY-03 (Alertmanager Watchdog)
```

## 동작 흐름

| 상황 | 결과 |
|------|------|
| 에러 로그 폭증 | 규칙이 빈도 임계 평가 → 그룹핑된 알림 1건 |
| 서비스 크래시 | 크래시 직전 로그는 전송될 수도, 안 될 수도 있음. **이후 로그 부재**는 규칙으로 감지 가능 (`absent_over_time`) |
| Alloy 다운 | 로그가 로컬 버퍼/파일에 남아 있으면 복구 후 전송, 아니면 **유실** |
| Loki 다운 | 규칙 평가 중단 → 알림 없음 (F7 영역) |

## 보장 속성

| 속성 | 수준 | 비고 |
|------|------|------|
| 유실 | **best-effort** | 수집 경로 버퍼에 의존. 트랜잭션 보장 없음 |
| 중복 | 규칙 평가 기반이라 알림 단위 중복은 Alertmanager가 처리 | |
| 개별 건 추적 | 로그 조회로 가능 | |
| 지연 | 수집 지연 + 평가 주기 (15~60s) | |

## 알림 실패 처리
Alertmanager의 재시도(webhook 실패 시) + notification-service의 사다리. 규칙 기반이라 **상태가 지속되면 다음 평가에서 다시 발화**한다(level-triggered 성격).

## 책임 경계 (DDD)
- 생산자는 "좋은 로그를 남길 책임"만 진다. 단 **로그 형식이 사실상 계약**이 된다(error_code 필드명이 바뀌면 규칙이 조용히 깨짐).
- 규칙 소유는 운영/플랫폼 팀. 도메인 지식(어떤 error_code가 중요한가)과 분리되기 쉬움.

## 트레이드오프

| 장점 | 비용 |
|------|------|
| 서비스 코드 결합 0 | 유실 가능 (best-effort) |
| 맥락이 풍부 (trace_id, order_id) | 로그 형식이 암묵적 계약 → 조용한 파손 |
| 기존 로그 재사용 — 추가 쓰기 경로 없음 | 수집·저장 인프라 비용 (로그량 비례) |
| 레거시 서비스에도 적용 가능 | 평가 주기만큼 지연 |
