# SG-01. messageId 왕복 핸드셰이크 (최초 설계)

> **상태**: 기준선 · **범주**: 단일 · **대상 실패**: F1, F2 (부분) · **id 의존도**: 매우 높음 (전달 확인 · dedup · 재시도 제어 전부)

문제 분석: [최초 설계 리뷰](../../01-problem/01-initial-design-review.md)

## 한 줄 요약
서비스가 실패마다 msgId를 붙여 알림 서비스로 보내고, msgId로 ack를 주고받아 처리 여부를 관리하며, 발송 실패가 누적되면 서비스에게 재시도를 요청한다.

## 핵심 아이디어
- 메시지 하나하나의 운명을 **양쪽이 msgId로 함께 추적**한다.
- 신뢰성을 "확인 메시지"로 얻는다.

## 전체 구조

```
 [도메인 경로]
 ┌──────────────────────┐ ① POST /alerts {msgId=UUID, payload}  ┌────────────────────────────┐
 │ order/product/shipping│──────────────────────────────────────▶│ notification-service        │
 │  ├ 비즈니스 트랜잭션   │                                        │  ├ inbox(msgId UNIQUE)      │
 │  ├ alert_status 테이블│◀────────── ② ack {msgId, status} ──────│  ├ 발송 워커 ──▶ Slack/Email │
 │  │  (SENT/ACKED/FAIL) │                                        │  └ 실패 카운트 배치(5분)     │
 │  └ POST /alerts/retry │◀── ③ count > N: "msgId 재시도" ─────────│                            │
 │     (payload 재발송)  │──── ④ 재발송 ──────────────────────────▶│                            │
 └──────────────────────┘                                        └────────────────────────────┘

 [흐름 경로]   없음 (각 서비스가 자기 실패만 보냄)
 [운영 경로]   원안: 없음
               실험 변형 SG-01+: SY-01(Prometheus/Alertmanager)만 부착해 "운영 경로 유무" 효과를 분리 측정
 [메타 경로]   없음
```

## 동작 흐름

**정상**
1. 서비스: 예외 발생 → 비즈니스 커밋 → msgId 생성 → `alert_status(msgId, SENT)` 기록 → POST
2. 알림: inbox INSERT → 발송 성공 → ack(ACKED) 회신
3. 서비스: `alert_status = ACKED`

**실패 시나리오**
| 상황 | 결과 |
|------|------|
| 커밋 후 POST 전 크래시 | msgId가 없음 → **추적 대상에서 소멸** (L6) |
| ack 유실 | 서비스는 미확인 → 재발송 → inbox 기록 시점에 따라 중복 (L1) |
| 발송 후 inbox 갱신 전 크래시 | 재시작 후 재발송 → Slack 중복 (L2) |
| Slack 장애 지속 | 재시도 명령 → 서비스 재발송 → 또 실패 → 증폭 루프 (L4) |
| 재시도 명령 유실 | 영구 미발송, 아무도 모름 (L5) |
| 알림 서비스 다운 | 모든 서비스에 미확인 건 누적, 감지 수단 없음 (P8) |

## 보장 속성

| 속성 | 수준 | 근거 |
|------|------|------|
| 유실 | **보장 안 됨** | dual write 공백(L6), 재시도 명령 유실(L5) |
| 중복 | 부분 억제 | inbox UNIQUE — 단 발송/갱신 비원자성(L2)으로 중복 가능 |
| 순서 | 보장 안 됨 | 재시도가 순서를 섞음 |
| 지연 | 정상 시 낮음, 실패 시 배치 주기(5분)+ | P10 |

## 알림 실패 처리
배치가 실패를 카운트 → 임계 초과 시 **생산자에게 재시도 명령**. 책임 사다리([담당과 라우팅 §4](../../01-problem/03-ownership-and-routing.md#4-알림-실패-처리--책임-사다리))와 반대 방향이다.

## 책임 경계 (DDD)
- 알림 전달 상태가 Upstream(비즈니스 서비스)과 Downstream(알림) 양쪽에 분산된다. 진실의 원천이 2개다(L7).
- Downstream → Upstream 명령이 존재한다(주객전도, P1).

## 트레이드오프

| 장점 | 비용 |
|------|------|
| 개념이 직관적이고 설명하기 쉽다 | 생산자마다 상태 테이블 + 재전송 API + ack 처리 코드 |
| 메시지 단위 상태를 양쪽에서 조회할 수 있다 | 양방향 시간 결합 — 알림 장애가 생산자 상태에 전파 |
| 브로커 없이 구현 가능 | 정합성 루프(L1~L7), 장애 시 트래픽 증폭 |

## 실험 가설
→ [실험 계획 · SG-01](../../04-experiments/experiment-plan.md#sg-01)
- H1: `crash-after-commit` 주입 시 주입 건수만큼 **유실이 발생**하고, 이 유실은 SG-01 내부 지표로는 관측되지 않는다.
- H2: Slack 5xx 지속 구간에서 서비스로 들어가는 재시도 트래픽이 시간에 따라 **증가**한다(증폭 루프).
- H3: 생산자 요청당 DB 쓰기가 SG-02 대비 많고(상태 테이블 + ack 갱신), 정상 흐름 p95가 높다.
