# FL-02. 이벤트 코레오그래피 + Saga 부재 감지 워치독

> **상태**: P1 · **범주**: 흐름 · **패턴**: 이벤트 코레오그래피 (Kafka) · **대상 실패**: F4 (주력), F3·F5 (부분) · **id 의존도**: 중간 — 흐름 정체성 **orderId/traceId**로 기대 이벤트를 대조

## 한 줄 요약
서비스들은 이벤트로만 연결되고 흐름 전체를 아는 주체가 없다. 그래서 **흐름을 관찰만 하는 워치독**을 두고, "이 이벤트 다음에는 N초 안에 저 이벤트가 와야 한다"는 기대를 기한과 함께 등록해 **오지 않으면 실패로 판정**한다.

## 핵심 아이디어
- 코레오그래피의 실패는 대부분 **부재**다. 배송 소비자가 멈추면 아무도 실패를 말하지 않는다.
- 워치독은 흐름에 참여하지 않는다(명령하지 않음). 이벤트를 **구독만** 하는 별도 소비자 그룹이다 → 흐름을 바꾸지 않고 붙였다 뗄 수 있다.
- 기대 규칙(Expectation)을 선언적으로 정의한다:
  ```
  OrderCreated   ─within 10s─▶ StockReserved | StockRejected
  StockReserved  ─within 10s─▶ ShipmentCreated | ShipmentFailed
  ShipmentFailed ─within 10s─▶ StockReleased              (보상 완료 기대)
  ```
- 기한 초과 = `FlowStuck{orderId, waitingFor, elapsed}` 알림. 기한의 2배 초과 = critical.
- 실패 이벤트(ShipmentFailed 등)가 **명시적으로** 오는 경우는 존재 신호 → 일반 알림. 워치독은 **안 오는 경우**를 담당한다.

## 전체 구조

```
 [흐름 경로 — 코레오그래피]
 order ─OrderCreated─▶ ┌──────────────── Kafka ────────────────┐
                       │ order-events / stock-events /          │
 product ◀─────────────│ shipment-events                        │
   └─StockReserved────▶│                                        │
 shipping ◀────────────│                                        │
   └─ShipmentCreated──▶│                                        │
   └─ShipmentFailed───▶│──▶ product: StockReleased (보상)        │
                       └───────────┬────────────────────────────┘
                                   │ (별도 consumer group: watchdog — 관찰 전용)
                                   ▼
 ┌──────────────────────────────────────────────────────────────────────┐
 │ Saga 워치독 (notification-service 내 모듈 또는 독립 서비스)            │
 │  expectations: {orderId, waitingFor[], deadline, traceId, step}       │
 │   - 이벤트 수신 → 기대 충족 시 삭제, 다음 기대 등록                     │
 │   - 스케줄러(1s): deadline < now → FlowStuck 발행                       │
 │  저장: notification_db (deadline 인덱스) — 재시작해도 기대 유지          │
 │  lag 보정: 워치독 자신의 consumer lag > 기한이면 판정 보류 (오탐 방지)  │
 └───────────────────────────────┬──────────────────────────────────────┘
                                 ▼
                     알림 파이프라인 (SG-04 집계: fp = hash(flow, waitingFor))
                     "StockReserved 후 ShipmentCreated 미도착 — 128건 (shipping consumer 정지 의심)"

 [도메인 경로]  각 서비스의 명시적 실패 이벤트(ShipmentFailed 등)도 같은 토픽에서 알림 파이프라인으로
 [흐름 진단]   FL-04: 이벤트 헤더로 traceparent 전파 → 비동기 구간도 하나의 trace로 연결
 [운영 경로]   SY-01: 서비스별 consumer lag, 워치독 expectations 개수·최고령, FlowStuck 발생률
               "shipping consumer lag 급증"(원인) ⟶ "FlowStuck 폭증"(증상) 억제 규칙
               SY-02: 서비스 /health
 [메타 경로]   SY-03 — 워치독 자신의 생존도 heartbeat로 감시 (워치독이 죽으면 F4가 조용해짐)
```

## 동작 흐름

| 상황 | 감지 | 알림 |
|------|------|------|
| shipping consumer 정지 | StockReserved 후 기한 초과 | FlowStuck (집계되어 1건) |
| 이벤트 유실 (발행 실패) | 다음 이벤트 미도착 → 기한 초과 | FlowStuck |
| ShipmentFailed 발행됨 | 존재 신호 | 일반 실패 알림 + 보상 기대 등록 |
| 보상 이벤트(StockReleased) 미도착 | 기한 초과 | **F5 critical** |
| 처리가 느릴 뿐 (부하) | 기한 초과 → 이후 도착 | FlowStuck → **늦은 도착 시 자동 해소(RESOLVED)** |
| 워치독 자신이 lag | lag 보정으로 판정 보류 | 오탐 없음, 대신 lag 알림(SY-01) |

### 기한 설정의 딜레마
- 짧으면: 부하 시 정상 흐름도 "정지"로 오탐 → 알림 피로
- 길면: 실제 정지를 늦게 앎
→ 기한은 정상 시 단계 지연 p99의 배수로 정하고, 실험(K2·K4)에서 오탐률과 감지 시간을 함께 측정해 조정한다.

## 보장 속성

| 속성 | 수준 | 비고 |
|------|------|------|
| 부재 감지 | 기한 내 보장 | 워치독이 살아 있는 한 |
| 오탐 | 기한 설정에 의존 | 늦은 도착 시 자동 해소로 완화 |
| 감지 지연 | 기한 + 스케줄러 주기 | |
| 워치독 상태 내구성 | DB 저장 | 메모리만 쓰면 재시작 시 진행 중 기대 소실 |

## 알림 실패 처리
FlowStuck은 알림 파이프라인(SG-02/03 + SG-04)으로 넘어간다. 사다리 동일.

## 책임 경계 (DDD)
- 코레오그래피에는 흐름 소유자가 **구조적으로 없다** → 워치독과 기대 규칙의 **소유팀을 명시적으로 지정**한다(주문 흐름 소유 = 주문팀).
- 워치독은 흐름의 **관찰자**이지 참여자가 아니다. 명령을 내리지 않으므로 서비스들의 자율성을 해치지 않는다.
- 기대 규칙이 흐름의 **암묵적 계약을 명시화**한 문서 역할도 한다.

## 트레이드오프

| 장점 | 비용 |
|------|------|
| 서비스 간 시간 결합 없음 — 하위 지연이 주문 응답에 영향 없음 | 흐름 실패 감지가 기한만큼 늦음 |
| 워치독을 붙였다 뗄 수 있음 (흐름 무변경) | 기한 튜닝 · 오탐 관리 |
| 이벤트 유실·소비자 정지까지 감지 | 기대 규칙이 실제 흐름과 어긋나면 조용히 틀림 (흐름 변경 시 규칙 동기화 필요) |
| 서비스 독립 배포·확장 | 디버깅이 어려움 → FL-04 필수 |

### FL-01과 비교
| | FL-01 동기 오케스트레이션 | FL-02 코레오그래피 + 워치독 |
|---|---|---|
| 감지 신호 | 존재 (응답) | 부재 (기한) |
| 감지 시점 | 즉시 | 기한 후 |
| 시간 결합 | 강함 | 없음 |
| 흐름 상태 위치 | 오케스트레이터 DB | 워치독(관찰 사본) + 각 서비스 분산 |
| 대표 위험 | 결과 불명, 연쇄 지연 | 오탐, 규칙-흐름 불일치 |

## 실험 가설
→ [실험 계획 · FL-02](../../04-experiments/experiment-plan.md#fl-02)
- H1: shipping consumer를 pause하면 **기한 + 스케줄러 주기 이내**에 FlowStuck이 발화하고, SG 계열 단독으로는 아무 알림도 발생하지 않는다.
- H2: shipping에 `latency` 주입 시 주문 응답 p95는 **변화 없음**(FL-01 H1과 대비), 대신 흐름 완료 지연이 늘고 기한이 짧으면 오탐이 발생한다.
- H3: 기한 3종(짧음/중간/김)에서 오탐률과 감지 시간의 트레이드오프 곡선을 얻는다.
- H4: 워치독 lag 보정이 없으면 워치독 재시작 직후 오탐이 대량 발생한다.
