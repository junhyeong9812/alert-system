# FL-05. Reconciliation Sweeper (사후 대조)

> **상태**: P2 · **범주**: 흐름 (공통 안전망) · **대상 실패**: F4, F5 (주력), 알림 누락 (보조) · **id 의존도**: 중간 — 대조 키는 **비즈니스 키(orderId)**

## 한 줄 요약
실시간 확인(ack, 워치독)을 하지 않고, **주기적으로 여러 서비스의 상태를 비교**해 어긋난 것을 찾는다. 다른 모든 방법론이 놓친 것을 잡는 최종 안전망이다.

## 핵심 아이디어
- 최초 설계의 L7(진실의 원천 분기)에 대한 정면 해법이다. 어긋남은 **일어난다고 가정**하고, 주기적으로 찾아서 수렴시킨다.
- 대조 규칙 예:
  - `order=CONFIRMED` 인데 `shipment` 없음 → 흐름 불일치
  - `order=FAILED` 인데 재고 차감이 복원되지 않음 → 보상 누락 (F5)
  - `order=UNKNOWN` (FL-01 타임아웃) → 하위 상태로 확정
  - 서비스 `failure_log`에 있는데 알림 inbox에 없음 → **알림 누락** (알림 파이프라인 자체 검증)
- 대조는 **안정 구간**에서만 한다: `updated_at < now() - settle_time`. 진행 중인 흐름을 불일치로 오판하지 않기 위해.

## 전체 구조

```
 [흐름 경로 — 대조]
 ┌───────────────────────────────────────────────────────────────────────┐
 │ reconciler (독립 배치 · 주기 1분 · notification-service 모듈 가능)       │
 │                                                                        │
 │  1. GET order/reconcile?from=&to=   → [{orderId, status, updatedAt}]   │
 │  2. GET product/reconcile?orderIds= → [{orderId, reserved, released}]  │
 │  3. GET shipping/reconcile?orderIds=→ [{orderId, shipmentStatus}]      │
 │  4. 규칙 평가 → 불일치 목록                                              │
 │  5. 불일치 → Mismatch 사실 발행 (fp = hash(rule)) → 알림 파이프라인       │
 │     (자동 교정은 하지 않음 — 이 프로젝트 범위에서는 감지까지)              │
 │  6. 체크포인트 저장 (마지막 대조 구간)                                    │
 └───────────────────────────────────────────────────────────────────────┘
   ※ 서비스 DB 직접 조회 대신 대조 전용 API (DB 결합 회피 — Open Host Service)

 [도메인/흐름 경로]  다른 방법론(SG/FL)과 병행 — 대체가 아닌 안전망
 [운영 경로]   SY-01: reconcile_run_duration, mismatch_total{rule}, last_success_timestamp
               "last_success_timestamp가 3주기 이상 갱신 안 됨" → reconciler 정지 알림
 [메타 경로]   SY-03
```

## 동작 흐름

| 상황 | 실시간 방법론 | Sweeper |
|------|-------------|---------|
| 워치독이 죽어 있던 동안의 정지 | 놓침 | 다음 주기에 불일치로 발견 |
| FL-01 타임아웃 결과 불명 | UNKNOWN으로 남음 | 하위 상태로 확정 → 불일치면 알림 |
| 보상 이벤트 유실 | 워치독 기한 초과(있으면) | 재고 미복원 발견 |
| 알림 파이프라인이 일부 유실 | 알 수 없음 | failure_log ↔ inbox 차이로 발견 |

## 보장 속성

| 속성 | 수준 | 비고 |
|------|------|------|
| 최종 감지 | 주기 + settle_time 내 | 지연이 크다 (분 단위) |
| 오탐 | settle_time에 의존 | |
| 부하 | 주기마다 대조 쿼리 | 구간 단위로 제한 |

## 알림 실패 처리
Mismatch 사실을 알림 파이프라인으로 넘긴다. 같은 불일치가 다음 주기에도 남아 있으면 다시 발견되므로 **자연스러운 재시도**가 된다(level-triggered 성격).

## 책임 경계 (DDD)
- 각 서비스는 대조 API(읽기 전용)만 제공한다.
- reconciler 소유는 흐름 소유팀. 대조 규칙 = 흐름 불변식의 명시적 표현.
- **자동 교정은 하지 않는다**: 교정은 도메인 결정(재고를 복원할지, 배송을 취소할지)이므로 해당 컨텍스트의 책임이다.

## 트레이드오프

| 장점 | 비용 |
|------|------|
| 실시간 메커니즘이 놓친 모든 것의 안전망 | 감지 지연 큼 (분 단위) |
| 메커니즘 독립 — 원인을 몰라도 결과로 잡음 | 대조 API · 규칙 유지 비용 |
| 알림 파이프라인 자체를 검증 | 데이터량 증가 시 대조 비용 |
| 구현 단순 | settle_time 튜닝 |

## 못 잡는 것
실시간성이 필요한 실패. 반드시 다른 방법론과 함께 쓴다.
