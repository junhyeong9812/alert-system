## 1. 환경

- 단일 호스트 24 코어 / 36 GB. compose 리소스: 서비스 mem 768m · cpus 2, order만 cpus 4, postgres 1g.
  - ⚠️ 실험 계획 §2의 잠정치(CPU 1 · 512MB)에서 바뀌었다. 512m/2cpu 콜드 실행에서 p50 2.56s·요청 드롭이 나서 가정 A1이 반증됐고, HTTP/1.1 고정 + 위 자원으로 올린 뒤 200 rps p95 61ms를 확인했다.
- 실행마다 상태 초기화 → 워밍업 120s → 본 측정 → cooldown 120s(적체 소진). 반복은 시나리오를 섞어 1회차 전체 → 2회차 전체 순으로 돌렸다.
- 알림 서비스 재시도 배치: 30s 주기, 임계 10건 **초과** 시 실패 건 전부에 재시도 명령. 생산자 ack 미수신 재발송: 30s 경과, 최대 3회.
- SG-01 실행 시 Prometheus·Alertmanager·Grafana는 정지. SG-01+ 실행(obs-servicedown plus1~3) 때만 기동.

## 2. 측정 신뢰성

- **K0 보정**: 알려진 실패 100건 → 도달 100 · 유실 0 · 중복 0. analyzer 파이프라인은 정상이다.
- **정답 분류**: 주입된 실패는 서비스 응답의 자체 오류 코드로 판정하고 셋으로 나눴다.
  - expect(알림이 와야 함)
  - unreached(대상 서비스에 도달하지 못함 — 연결 거부·주소 해석 실패)
  - unknown(타임아웃 — 결과 불명)

  unreached와 unknown은 유실 계산에서 뺐다.
- **교차 검증**: 생산자 DB의 '실패 기록 수 대 `alert_status` 행 수' 차이(dual-write 공백)와 analyzer가 센 유실이 FI-07에서 모든 반복마다 일치했다(5 = 5).

## 3. 시나리오별 결과

### K1 · 기준 부하(장애 없음, 50→100→200 rps)

| 구간 | p50 ms | p95 ms | p99 ms | 의도치 않은 실패 |
|------|--------|--------|--------|------------------|
| 50 rps | 15.4 | 23.9 | 31.9 | 0 |
| 100 rps | 20.0 | 32.2 | 43.8 | 0 |
| 200 rps | 21.4 | 48.1 | 71.1 | 0 |

- 요청 63,002건 전부 성공, 알림 0건.
- SG-01은 실패가 있을 때만 생산자 DB에 쓴다(`alert_status` insert 1회 + ack update 1회). 그래서 장애가 없으면 알림 경로의 오버헤드도 0이다.

### K2 · 혼합 정상상태(100 rps 10분, biz 10% · tech 5% · latency 5%)

- 정답 9,023(9,023/9,068/8,999) → 도달 9,023 · 유실 0 · 중복 0. 생산자 상태는 전부 `ACKED`, inbox는 전부 `SENT`.
- e2e(실패 발생 → Slack 수신) p50 130ms · p95 227ms. 흐름 p95 78.4ms · p99 318ms(latency 주입 영향).

### K3 · 실패 폭주(100 rps, t=2~3분 shipping:tech 50%)

- 정답 2,981 → 도달 2,981, 유실 0. e2e p95 255ms. 흐름 p95는 calm 31.1ms → storm 53.2ms.
- **사람이 본 알림 2,981건 = 실패 건수.** 1분 폭주가 그대로 알림 2,981건이 됐다. 묶음 처리가 없는 기준선의 알림 피로 수치이며, SG-04와 비교할 기준이다.

### K6 · FI-07 커밋 후 크래시 → **H1 채택**

| | r1 | r2 | r3 |
|---|---|---|---|
| 정답(expect) | 313 | 308 | 329 |
| 유실 | **5** | **5** | **5** |
| shipping 실패기록 \| alert_status | 107 \| 102 | 130 \| 125 | 137 \| 132 |
| shipping 생산자 `SENT`(미확인) | 1 | 1 | 1 |
| 미도달 / 불명(제외) | 2 / 68 | 1 / 66 | 4 / 59 |

- 크래시 5회 = 유실 5 = DB 공백 5가 모든 반복에서 맞았다. 업무 커밋 후 `alert_status` 기록 전에 프로세스가 죽으면 생산자에게는 '보낼 것'이 없다.
- SG-01의 유일한 내부 신호는 '미확인(`SENT`) 건수'인데, 여기에는 **1건만** 남았다. 이 1건은 유실과 무관한 건으로, 크래시 순간 ack 콜백이 실패한 경우다(`ack_total{result="error"}` 1). **유실 5건은 어떤 내부 지표에도 나타나지 않았다.**
- 의도치 않은 실패 1,197건은 shipping 재기동 중 배경 흐름이 실패한 것이다(크래시의 부수 효과).

### K6 · FI-09 채널 5xx 60초(t=60~120s) → **H2 채택(제한적)**

채널 시도(수락/거절)를 30초 버킷으로 나눈 결과. 평상시 도착은 약 150건/30s.

| 버킷 | 0s | 30s | 60s | 90s | 120s | 150s | 180s |
|------|----|-----|-----|-----|------|------|------|
| r1 | 159/0 | 136/0 | 0/182 | **0/334** | **461/0** | 135/0 | 144/0 |
| r2 | 142/0 | 157/0 | 1/191 | 0/228 | **424/0** | 137/0 | 138/0 |
| r3 | 145/0 | 149/0 | 0/270 | **0/364** | **434/0** | 156/0 | 154/0 |

- 장애 구간의 거절은 516건(516/419/634)이고, 재시도 명령도 516건이다. 장애 중 도착은 약 300건이므로 약 200건(1.7배)이 재시도 배치 → 생산자 재전송으로 되돌아와 다시 거절된 것이다.
- 복구 직후 버킷이 424~461건으로 평상시의 약 3배다. 적체 + 재전송분이 한꺼번에 쏟아진다.
- 최종 유실은 0이지만, 영향을 받은 건의 e2e p95는 **56.4s**(46.2/56.4/68.9), 최대 72s다. 재시도 배치 주기(30s)와 위상에 묶인다.
- 증가는 장애 길이(60s ≈ 배치 2주기)에 비례했고, 무한 증폭은 없었다. 재시도는 실패 건마다 정확히 한 번 명령되기 때문이다(fail 수 = retry_cmd 수). 다만 채널을 살리는 것과 무관한 생산자 3곳에 트래픽을 되돌려 보낸다는 구조, 즉 L4 역방향 의존은 수치로 확인됐다.

### K6 · FI-14 중복 전송 + 콜백 차단 60초 → L1 재현, **L7 재현**

| | r1 | r2 | r3 |
|---|---|---|---|
| 정답 / 도달 / 중복 | 700 / 700 / 0 | 727 / 727 / 0 | 752 / 752 / 0 |
| ack 미수신 재발송 (`alert_ack_resend_total`) | 684 | 702 | 729 |
| ack 콜백 실패 | 228 | 234 | 243 |
| 생산자 최종 `ACKED` / `SENT` | 472 / **228** | 493 / **234** | 509 / **243** |
| inbox 최종 | 전부 `SENT` | 전부 `SENT` | 전부 `SENT` |

- **L1(ack 미수신 재발송) 재현**: 콜백이 막힌 동안 생산자는 같은 msgId로 상한 3회까지 재발송했다.
- 사람이 본 중복은 0이다. inbox가 수신 시점에 msgId로 dedup하기 때문이다. 즉 SG-01에서 중복을 막는 장치는 '왕복 ack'가 아니라 '수신측 inbox'다.
- **L7(진실의 원천 분기)**: 콜백 실패 수 = 생산자 `SENT` 잔류 수가 정확히 일치한다. 이미 `SENT`인 건이 재발송되면 inbox는 dedup으로 무시하고 ack를 다시 보내지 않는다. 그래서 생산자는 상한까지 재발송한 뒤 '미확인'에서 멈춘다. 같은 알림이 알림 서비스에서는 '발송 완료', 생산자에서는 '미확인'으로 영구히 갈린다.
  - 생산자의 미확인 지표는 이 228~243건을 '문제'로 보고하지만 실제로는 모두 발송됐다(오탐).
  - FI-07에서는 반대로 실제 유실 5건을 보고하지 못했다(미탐).
  - 결국 SG-01의 내부 신호는 오탐과 미탐을 모두 낸다.

### SG-01+ · 서비스 다운(shipping kill → 90s 정지) — 운영 경로 효과

| | SG-01 (r1) | SG-01+ (plus1/2/3) |
|---|---|---|
| ServiceDown 감지 | **없음** | 47.6 / 46.2 / 44.2 s |
| 운영 알림 | 0 | 4 (ServiceDown·HighErrorRate order, 각 FIRING+RESOLVED) |
| 도메인 알림 유실 | 0 | 0 / 0 / 0 |
| 미도달(제외) | 719 | 697 / 680 / 676 |

- 감지 시간 ≈ 스크레이프 주기 + `for: 30s`이다. 정지된 shipping은 끝까지 정지 상태였다(재시작으로 인한 위장 복구 없음).
- 다운 동안 shipping으로 가는 주입 약 690건은 **실패 사실 자체가 생기지 않아**(미도달) 도메인 알림 경로로는 원리적으로 잡을 수 없다. 운영 경로가 없으면 '서비스가 죽었다'를 알 수단이 0이다. 이것이 RQ7의 기준값이다.
- SG-01+ 쪽 HighErrorRate order 알림은 원인(shipping 다운)의 증상이다. 원인 1건에 알림 2종이 나온다(FL/SY 단계에서 묶음 대상).

## 4. 한계와 해석 주의

1. **채널 장애는 운영 경로로도 감지되지 않는다.** SG-01+ 규칙은 ServiceDown·HighErrorRate(흐름 5xx) 두 개뿐이다. Slack 5xx는 흐름 오류가 아니고, `notifier_send_total{result="error"}` 지표는 있지만 규칙이 없다. Phase 1에서는 SG-01+ × FI-09 조합을 돌리지 않았으며, 이 판단은 규칙 구조에 근거한다. 채널 실패 감지는 SY-01 전체 규칙셋과 SY-03(메타 감시)의 몫이다.
2. **Slack 성공·Email 실패 = 전체 실패(R12).** critical 알림에서 한 채널만 실패하면 전체를 실패로 보고하고, 재시도 때 성공했던 채널에도 다시 보낸다. 원안에 채널별 상태가 없어서 생기는 기준선 결함이며, 이번 시나리오(Email 장애 없음)에서는 발현되지 않았다.
3. **재시도 배치 위상.** 배치는 기동 시점 기준 30s 주기라 장애 구간과의 위상이 반복마다 다르다. FI-09 거절 수(419~634)와 e2e p95(46~69s)의 편차가 주로 여기서 나온다.
4. **불명(unknown) 제외.** FI-07에서 66건, servicedown에서 34~72건이 order 타임아웃으로 결과 불명이라 유실 계산에서 뺐다. 이 중 실제로 알림이 온 건은 '불명 도달'로 따로 셌다. FL-01의 '결과 불명' 문제 자체이며, 기준선의 유실 0은 이 제외를 전제로 한다.
5. **카운터는 재시작 시 0.** 크래시·kill로 재시작한 서비스의 카운터 증분은 과소다. 예: FI-07 shipping `alert_send_total` 13~21, servicedown plus2 shipping 44. 유실·상태 판정은 카운터가 아니라 sink 기록과 DB로 했다.
6. **콜백 타임아웃 산물.** 크래시 순간의 ack 실패 1건(FI-07)은 하네스가 아니라 SG-01 구조에서 나온 결과이지만, 발생 여부는 크래시 타이밍에 달려 있다.
7. **재시도 명령 후 재발송 카운트.** `retry()`는 `ack_resend_count`를 리셋하지 않는다. 총 재발송 상한으로 의도한 것이다.
8. **자원 설정 변경(A1).** 계획 잠정치보다 큰 자원으로 측정했다. 방법론 간 비교는 같은 compose에서 하므로 상대 비교에는 영향이 없지만, 절대 지연을 다른 환경과 비교할 수는 없다.
