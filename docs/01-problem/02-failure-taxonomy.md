# 실패 유형 분류

> 방법론을 고르기 전에 "무엇을 잡아야 하는가"를 분리한다.
> 실패 유형마다 **신호의 형태**가 다르고, 신호의 형태가 감지 방식을 결정한다.

## 1. 분류 축

| 축 | 질문 | 값 |
|----|------|-----|
| **발생 위치** | 어디서 났나 | 단일 서비스 / 흐름(서비스 횡단) / 시스템·인프라 / 알림 경로 |
| **신호 형태** | 무엇으로 알 수 있나 | **존재**(이벤트가 있음) / **부재**(기대한 것이 없음) / **상태**(측정값이 이상함) |
| **자가 보고 가능성** | 실패한 서비스가 스스로 알릴 수 있나 | 가능 / 불가능 |

```
                 자가 보고 가능                          자가 보고 불가능
          ┌───────────────────────────────┬───────────────────────────────┐
  존재    │ F1 비즈니스 실패               │                               │
          │ F2 기술 예외                   │                               │
          │ F3 흐름 전파 실패 (호출자가 보고)│                               │
          ├───────────────────────────────┼───────────────────────────────┤
  부재    │                               │ F4 흐름 부재·정지              │
          │                               │ F5 보상 실패 (일부)            │
          ├───────────────────────────────┼───────────────────────────────┤
  상태    │ (F1·F2의 비율 이상)            │ F6 시스템·인프라               │
          │                               │ F7 알림 경로                   │
          └───────────────────────────────┴───────────────────────────────┘
       push로 잡힌다 ◀──────────────────────────────▶ pull·타임아웃·외부 관측이 필요
```

최초 설계(push + id)는 **왼쪽 위 칸만** 다룬다.

## 2. 실패 유형

### F1. 단일 — 비즈니스 실패
- **예**: 재고 부족, 결제 거절, 배송 불가 주소, 주문 한도 초과
- **성격**: 예상된 도메인 결과. 서비스는 정상이고 "규칙대로 거절"한 것이다.
- **신호**: 존재(도메인 이벤트) · 자가 보고 가능
- **알림 판단**: 개별 건은 대개 알림 대상이 아니다. **비율 이상**(평소 재고 부족 1% → 지금 40%)이 알림 대상이다. 단 고가치 건(대량 주문 등)은 개별 알림이 될 수 있다.

### F2. 단일 — 기술 예외
- **예**: DB 쿼리 타임아웃, NPE, 직렬화 오류, 외부 API 5xx, 커넥션 획득 실패
- **성격**: 서비스 프로세스는 살아 있지만 요청 처리에 실패했다.
- **신호**: 존재(예외 이벤트/로그) + 상태(에러율 메트릭) · 자가 보고 가능
- **알림 판단**: 같은 원인의 반복이 많아 **문제 단위 묶음 처리**가 핵심이다.

### F3. 흐름 — 전파 실패 (동기 오케스트레이션)
- **예**: Order가 Product를 호출했는데 5xx/타임아웃 → 주문 실패 처리 → 이미 수행된 단계를 보상
- **성격**: 실패가 호출 스택을 타고 호출자에게 돌아온다. 호출자(오케스트레이터)가 실패를 안다.
- **신호**: 존재(오케스트레이터가 보고) · 자가 보고 가능
- **특이점 — 타임아웃의 불확실성**: 하위 호출이 타임아웃되면 하위가 **실제로 성공했는지 모른다.** 재고는 차감됐는데 주문은 실패로 처리되는 불일치가 생길 수 있다. 이 불확실 상태 자체가 알림 대상이다.

### F4. 흐름 — 부재·정지 (이벤트 코레오그래피)
- **예**: `OrderCreated` → `StockReserved`까지 발행됐는데 `ShipmentCreated`가 오지 않음 (배송 소비자 정지, 이벤트 유실, 처리 중 무한 대기)
- **성격**: 아무도 실패를 보고하지 않는다. 실패는 "일어나지 않음"으로 존재한다.
- **신호**: 부재 · 자가 보고 불가능
- **감지 원리**: 기대 이벤트에 **기한**을 두고, 기한이 지나도 오지 않으면 실패로 판정한다.

### F5. 흐름 — 보상 실패
- **예**: 배송 생성 실패 → 재고 복원(보상) 호출 → 재고 복원도 실패
- **성격**: 시스템이 **데이터 불일치 상태로 남는다.** 자동 복구 경로가 소진된 상태다.
- **신호**: 존재(보상 실패를 아는 경우) 또는 부재(보상 이벤트가 오지 않는 경우)
- **알림 판단**: 가장 높은 심각도. 사람의 수동 개입이 필요하다.

### F6. 시스템·인프라
- **예**: 프로세스 사망(OOM, panic), 커넥션 풀 고갈, 디스크 풀, DB/브로커 다운, 네트워크 지연·분할, CPU 포화
- **성격**: 서비스 자체가 정상적으로 동작하지 않거나 존재하지 않는다.
- **신호**: 상태 · 자가 보고 불가능 (죽은 서버는 말할 수 없다)
- **감지 원리**: 외부에서 **주기적으로 관측(pull)**하고, 관측 실패 자체를 신호로 쓴다.

### F7. 알림 경로
- **예**: 알림 서비스 다운, Slack 5xx/429(rate limit), SMTP 실패, DLQ 적체, Prometheus/Alertmanager 다운
- **성격**: 다른 모든 실패를 전달해야 할 경로 자체의 실패. **"감시자는 누가 감시하나"** 문제다.
- **신호**: 상태(메타) · 자가 보고 불가능
- **감지 원리**: 알림 경로 **바깥**의 독립된 감시(dead man's switch).

## 4. 경계 사례 — 유형이 겹칠 때

### 같은 원인, 여러 유형으로 보임
```
 원인: Postgres 다운 (F6)
   ├─ Order:    DB 예외 300건/분 (F2)
   ├─ Product:  DB 예외 280건/분 (F2)
   └─ Shipping: DB 예외 310건/분 (F2)
```
- 그대로 두면 원인 알림 1건 + 증상 알림 수백 건이 쏟아진다.
- **억제(inhibition)**: 상위 원인 알림(F6 DB 다운)이 발화 중이면 하위 증상 알림(F2)은 억제한다. Alertmanager의 `inhibit_rules`가 이 개념이다.

### F1 폭증은 사실 F2/F6일 수 있다
- 재고 서비스 버그로 모든 요청에 "재고 부족"을 반환하면, 겉보기엔 F1(정상 비즈니스 결과)이지만 실제로는 F2(결함)다.
- 개별 건만 보면 구분할 수 없다. **비율 기반 감시(상태 신호)**가 F1에도 필요한 이유다.

### F3 타임아웃은 F5의 씨앗
- 하위 호출이 타임아웃되면 성공 여부를 모른 채 보상을 시도하게 된다. 보상이 "없는 차감을 복원"하면 재고가 늘어나는 불일치가 생긴다.
- 타임아웃 건은 "결과 불명" 상태로 분리해 추적하고, 사후 대조(FL-05)의 대상으로 삼는다.

### F7은 다른 유형의 감지를 모두 무력화한다
- 알림 경로가 죽으면 F1~F6가 전부 "조용해진다." **조용함은 정상과 구분되지 않는다.**
- 그래서 F7 감시는 "알림이 오지 않으면 이상"이라는 역전된 논리(heartbeat 부재)를 쓴다.

## 5. 신호 형태가 감지 방식을 결정한다

| 신호 형태 | 감지 방식 | 핵심 메커니즘 | 약점 |
|----------|----------|--------------|------|
| 존재 | push | 이벤트 발행 → 소비 | 보낸 것만 안다 |
| 부재 | 타임아웃 | 기대 목록 + 기한 | 기한 설정이 어렵다 (짧으면 오탐, 길면 늦음) |
| 상태 | pull | 주기적 측정 + 규칙 평가 | 해상도가 주기에 묶인다, 개별 맥락이 빈약 |

**어떤 단일 방법론도 세 신호를 모두 다루지 못한다.** 그래서 방법론은 단일/흐름/시스템 범주로 나뉘고, 최종 구조는 범주별 방법론을 조합한 통합 구조가 된다([IN-01](../03-methodologies/integrated/in-01-integrated-architecture.md)).
