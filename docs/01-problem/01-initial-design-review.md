# 최초 설계 리뷰 — messageId 왕복 핸드셰이크

> 기술면접에서 제시한 설계를 있는 그대로 정리하고, 어디가 왜 문제인지 분석한다.
> 결론부터: **id가 나쁜 것이 아니라, id 하나에 너무 많은 역할(전달 확인 · 중복 제거 · 추적 · 재시도 제어)을 맡긴 것이 문제**다.

관련: [실패 유형 분류](02-failure-taxonomy.md) · [담당과 라우팅](03-ownership-and-routing.md) · 방법론 문서 [SG-01](../03-methodologies/single/sg-01-id-ack-handshake.md)

---

## 1. 최초 설계

```
 ┌──────────────┐ ① 실패 발생 → msgId 생성 → POST {msgId, payload}   ┌────────────────────┐
 │ Order 서비스 │──────────────────────────────────────────────────▶│ Notification 서비스│
 │              │                                                    │  ② inbox(msgId) 기록│
 │ msg 상태 테이블│◀─────────────── ③ ack(msgId) ─────────────────────│  ② 채널 발송        │──▶ Slack/Email
 │ (SENT/ACKED) │                                                    │                    │
 │              │◀── ⑤ [배치] 실패 count > N → "msgId 재시도해라" ───│  ④ 실패 카운트 배치 │
 │ 재전송 API   │──────────────── ⑥ 재발송(msgId, payload) ─────────▶│                    │
 └──────────────┘                                                    └────────────────────┘
```

1. 서비스는 예외가 나면 `msgId`를 만들어 알림 서비스로 보낸다.
2. 알림 서비스는 `msgId`로 inbox에 기록하고 채널(Slack/Email)로 발송한다.
3. 처리 결과를 `msgId`로 서비스에 다시 알려(ack) 서비스가 처리 여부를 관리한다.
4. 발송 실패는 배치가 주기적으로 카운트한다.
5. 카운트가 임계치를 넘으면 서비스에게 "해당 msgId를 재시도하라"고 요청한다.
6. 서비스는 해당 msgId의 payload를 다시 보낸다.

## 2. 이 설계가 맞게 본 것

문제점만 있는 설계는 아니다. 다음은 그대로 살릴 가치가 있다.

- **inbox 패턴**: 수신 측이 받은 것을 기록해 중복 수신을 걸러낸다는 발상은 맞다.
- **"알림도 실패할 수 있다"는 인식**: 많은 설계가 알림을 fire-and-forget으로 놓친다.
- **임계치 기반 대응**: 일시적 실패와 지속적 실패를 구분하려는 시도다.

문제는 이 요소들이 **어느 컨텍스트에 놓여 있고, id가 어떤 역할을 떠맡고 있는가**에 있다.

## 4. 각 문제가 왜 문제인가

### P1. 책임 역전 (DDD 주객전도)

```
  올바른 경계                                   최초 설계
  Order ── 사실 기록 ══▶ Notification           Order ◀══ "재시도해라" ══ Notification
         (여기서 책임 종료)   └ 전달·재시도         └ payload 보관, 재전송 API, 상태 관리
```

- 예외의 주인은 Order가 맞다. 하지만 **알림 서비스가 그 사실을 받은 순간부터 "Slack에 못 보냈다"는 알림 컨텍스트의 실패**다.
- "msgId 재시도해라"는 하위(Downstream) 컨텍스트가 상위(Upstream) 컨텍스트에 명령하는 구조다. Order는 Slack이 뭔지 몰라야 하는데, 알림 정책(재시도 시점·횟수)이 Order 코드로 새어 들어온다.
- 결과적으로 알림 채널이 추가·변경될 때마다 모든 비즈니스 서비스가 영향을 받는다.

### P2. 양방향 시간 결합

- Order는 ack를 받아야 "처리 완료"로 판단한다. 알림 서비스가 느려지거나 죽으면 Order의 상태 테이블에 미확인 건이 쌓인다.
- ack 대기를 동기로 구현하면 Order의 응답 지연에 알림 서비스 지연이 그대로 더해진다. 비동기로 구현해도 미확인 건을 관리하는 로직이 Order에 남는다.
- **알림은 부가 기능인데, 부가 기능의 장애가 핵심 기능의 상태 관리에 들어와 있다.**

### P3. id 정합성 문제 루프 → [§5에서 상세](#5-id-정합성-문제-루프)

### P4. 원자성 공백 (dual write)

```
 Order: BEGIN; UPDATE order SET status='FAILED'; COMMIT;   ← 커밋 완료
        ── 여기서 프로세스 크래시 ──
        POST /alerts {msgId, ...}                          ← 실행되지 않음
```

- msgId는 전송 시점에 생성되므로, 커밋 후 전송 전에 죽으면 **msgId조차 존재하지 않는다.** id 기반 추적 시스템이 그 실패의 존재를 모른다.
- id를 아무리 정교하게 관리해도 "id가 생기기 전"의 유실은 막을 수 없다. 비즈니스 상태 변경과 알림 의도 기록을 **같은 트랜잭션**에 묶어야 한다(→ [SG-02](../03-methodologies/single/sg-02-outbox-idempotent-inbox.md)).

### P5. dedup 단위 오류 — 메시지 vs 문제

- DB 커넥션 풀이 고갈되면 1분에 같은 예외가 1,000건 난다. msgId도 1,000개다.
- msgId 기반 dedup은 "같은 메시지의 중복"만 거르지, "같은 문제의 반복"은 거르지 않는다. 결과는 **Slack에 1,000건**이다.
- 알림에서 진짜 해결할 문제는 정확히 한 번 전달보다 **알림 피로(alert fatigue)**다. 사람이 보는 알림 수는 메시지 수가 아니라 문제 수에 비례해야 한다(→ [SG-04](../03-methodologies/single/sg-04-fingerprint-aggregation.md)).

### P6. 부재 실패 미감지

- 이벤트 코레오그래피에서 상품 차감까지 성공했는데 배송 서비스 소비자가 멈추면, **아무도 실패 메시지를 보내지 않는다.** 실패가 "무언가가 일어나지 않음"의 형태로 존재한다.
- push 기반 id 시스템은 보낸 것만 추적한다. 보내지 않은 것은 추적 대상이 아니다(→ [FL-02](../03-methodologies/flow/fl-02-choreography-watchdog.md)).

### P7. 시스템 실패 미감지

- OOM으로 죽은 프로세스, 커넥션 풀이 고갈돼 응답하지 못하는 서버는 msgId를 만들 수 없다.
- 시스템 실패는 **외부에서 상태를 관측(pull)**해야 한다(→ [SY-01](../03-methodologies/system/sy-01-level-triggered-metrics.md), [SY-02](../03-methodologies/system/sy-02-blackbox-probing.md)).

### P8. 감시자 미감시

- 알림 서비스가 다운되면 실패 카운트 배치도, 재시도 요청도 멈춘다. 그 사실을 알릴 경로가 알림 서비스 자신이다.
- 알림 경로의 생존은 **알림 경로 바깥**에서 확인해야 한다(→ [SY-03](../03-methodologies/system/sy-03-dead-mans-switch.md)).

### P9. 비대칭 비용 무시

| 도메인 | 중복의 비용 | 유실의 비용 | 적절한 보장 |
|--------|------------|------------|-------------|
| 결제 | 치명적 (이중 출금) | 치명적 | effectively-once (멱등키 필수) |
| 알림 | 낮음 (같은 메시지 2번) | 높음 (장애를 모름) | at-least-once + 의미 단위 묶음 |

- 알림은 "중복은 견딜 수 있고 유실은 견딜 수 없는" 도메인이다. 왕복 ack로 정확히 한 번에 다가가려는 비용(상태 테이블, 회신 채널, 재시도 명령)이 얻는 가치보다 크다.

### P10. 배치 카운트의 지연과 상태

- 배치 주기가 5분이면 지속적 발송 실패를 최대 5분 늦게 안다. 그동안 알림은 계속 쌓인다.
- 카운터는 어디에 저장되나? 알림 서비스가 재시작하면 리셋되나? 카운트 기준(msgId별? 채널별?)은? — **카운터 자체가 정합성을 관리해야 할 새로운 상태**가 된다.
- 게다가 실패 원인이 채널(Slack 장애)이면 생산자에게 재시도를 시켜도 해결되지 않는다(→ §5 L4).

### P11. 역할 혼동

- 흐름 실패를 진단할 때 필요한 것은 "이 실패가 어느 주문 흐름의 몇 번째 단계에서 났나"라는 **인과 정보(traceId/correlationId)**다.
- 전달 확인용 msgId는 알림 메시지 하나의 정체성이고, traceId는 비즈니스 흐름의 정체성이다. 하나로 묶으면 둘 다 제대로 하지 못한다(→ [FL-04](../03-methodologies/flow/fl-04-trace-correlation.md)).

## 5. id 정합성 문제 루프

id로 "확인"을 하려면 확인 메시지가 필요하고, 그 확인 메시지도 유실될 수 있으므로 다시 확인이 필요하다. 이것은 분산 시스템의 **Two Generals 문제**이며, 메시지를 더 보내서는 끝나지 않는다.

### L1. ack 유실 → 재전송 → 중복 발송

```
 Order                     Notification                Slack
   │── msg#7 ─────────────────▶│── 발송 ──────────────────▶│ ✔ (1번째)
   │          ack#7 ✕ (유실)  │
   │   (타임아웃: 미확인)       │
   │── msg#7 재전송 ──────────▶│ inbox에 #7 있음 → 스킵?    │
```
- inbox가 #7을 걸러내면 다행이지만, **inbox 기록 전에 발송했다면**(L2) 중복이 된다. ack 유실 하나로 생산자는 "보낼까 말까"를 판단할 근거를 잃는다.

### L2. 발송 후, 상태 갱신 전 크래시 → 중복 Slack

```
 Notification: inbox#7=PENDING → Slack 발송 ✔ → ── 크래시 ── → inbox#7=SENT (실행 안 됨)
 재시작:       inbox#7=PENDING 발견 → 다시 발송 → Slack 2번
```
- 외부 부작용(Slack API 호출)과 로컬 상태 갱신은 **원자적으로 묶을 수 없다.** 어떤 순서로 하든 크래시 지점에 따라 유실이나 중복 중 하나가 발생한다.
- 따라서 어떤 설계든 at-least-once(중복 허용)를 고르게 된다. 그렇다면 id 왕복으로 중복을 막으려는 노력의 상당 부분은 애초에 달성 불가능하다.

### L3. 비결정적 id → dedup 무력화

```
 1차 시도: msgId = UUID.random() → a1b2…
 재시도:   msgId = UUID.random() → f9e8…   ← 같은 실패인데 다른 id
```
- 재시도 경로에서 id를 새로 만들면 inbox는 같은 실패를 구분하지 못한다. id는 **결정적**(aggregateId + eventType + version 같은 내용 기반)이어야 의미가 있다.

### L4. 재시도 명령 증폭 루프 (retry storm)

```
 Slack 장애 중
 Notification: 발송 실패 → count++ → count > N → Order에 "msg#7 재시도"
 Order:        msg#7 재발송
 Notification: 발송 실패 (Slack 여전히 장애) → count++ → 또 "재시도" …
                       └─────────────── 루프 ───────────────┘
```
- 실패 원인이 **생산자가 아니라 채널**인데 생산자를 재시도시킨다. 원인과 무관한 곳을 흔드는 셈이다.
- 장애 메시지 수 × 재시도 명령만큼 트래픽이 증폭되어, 장애 시점에 정상 서비스까지 부하를 받는다.

### L5. 재시도 명령 자체의 유실 → 무한 회귀

```
 Notification ── "msg#7 재시도" ──✕ (유실) ──▶ Order
```
- 재시도 명령도 메시지다. 이것이 유실되면 msg#7은 영구 미발송이 된다.
- 명령의 도착을 보장하려면 명령에도 id와 ack가 필요하고, 그 ack도 유실될 수 있다 → **확인의 확인의 확인…** 끝나지 않는다.

### L6. 존재 이전의 유실 (dual write, P4)

```
 비즈니스 커밋 ✔ → 크래시 → msgId 생성 전
```
- id 시스템의 관측 범위 밖에서 일어난 유실이다. id를 늘려서는 절대 잡히지 않는다.

### L7. 진실의 원천 분기

```
 Order 상태 테이블:     msg#7 = ACKED
 Notification inbox:    msg#7 = FAILED (재시도 소진)
```
- 양쪽이 같은 사실의 상태를 각자 들고 있으면 언젠가 어긋난다. 어긋남을 바로잡으려면 결국 **양쪽을 대조하는 로직(reconciliation)**이 필요하다. 그렇다면 처음부터 사후 대조로 정합성을 맞추는 편이 더 단순하다(→ [FL-05](../03-methodologies/flow/fl-05-reconciliation-sweeper.md)).

### 루프의 구조

```
   "전달을 확인하자" ──▶ 확인 메시지(ack) 추가
          ▲                      │
          │                      ▼
   "확인 메시지도 확인하자" ◀── ack도 유실 가능
```

**탈출구는 메시지를 더 보내는 것이 아니라, 문제의 성격을 바꾸는 것이다.**

| 탈출 전략 | 바꾸는 것 | 방법론 |
|-----------|----------|--------|
| 단방향 책임 이전 | "받았다"(202)로 생산자 책임 종료, 회신 채널 제거 | SG-02, SG-03 |
| 멱등성 | 중복을 막지 않고 **무해하게** 만듦 (결정적 키) | SG-02 |
| 내구성 있는 로그 | 메시지별 ack 대신 **위치(오프셋/커서)**로 진행 관리 | SG-03, SG-06 |
| 상태 기반 재평가 | 이벤트를 잃어도 다음 평가에서 다시 발화 | SY-01 |
| 사후 대조 | 실시간 확인 대신 주기적 비교로 수렴 | FL-05 |

## 6. 결론 — id를 버리는 게 아니라 역할을 재배치한다

| 역할 | 최초 설계 | 재배치 |
|------|----------|--------|
| 중복 무해화 | 무작위 msgId + ack | **결정적 멱등키** (내용 기반) |
| 진행 상태 관리 | 메시지별 ack | **오프셋 / 커서** (로그 위치) |
| 알림 중복 억제 | msgId | **fingerprint** (문제 정체성) |
| 흐름 진단 | msgId | **traceId / correlationId** (인과) |
| 실험 검증 | — | **테스트 하네스 id** (관측 전용, 아키텍처 로직에 미사용) |

면접 답변의 골격:
> "id 자체에 집착하기보다, 먼저 보장해야 할 속성 — 유실 없음, 중복 허용 범위, 추적성, 감시 범위 — 을 정의하고 속성마다 가장 싼 메커니즘을 고릅니다.
> 알림은 중복보다 유실이 비싼 도메인이라 at-least-once + 의미 단위 묶음이면 충분하고, 생산자의 책임은 사실을 내구성 있게 넘기는 데서 끝나야 합니다.
> 이벤트가 오지 않는 실패와 서버 자체의 실패는 push로 잡을 수 없으니 부재 감지와 외부 모니터링으로 분리합니다."
